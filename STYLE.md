# SF-in-Lean Style Guide

This file records the **normative** style conventions for *Software Foundations
in Lean* (SFL): how the material itself should be written, structured, and read.
Every contribution — human or AI — is expected to follow it. `CONTRIBUTING.md`
covers *workflow and mechanics* (how to build, branch, and submit); this file
covers *style*.

Where a convention below is not (yet) enforced by a tool, follow it anyway.
Deviations are permitted only for a strong pedagogical reason (Guiding
Philosophy, tenet 3) and must be **marked at the point of deviation** with a
short note naming the convention and the reason — see
[Checking these conventions](#checking-these-conventions).

Each convention has a stable **ID** (`LEAN-*`, `PED-*`, `WRITE-*`) so that
automated checks, review reports, and deviation markers can refer to it
unambiguously. Add new conventions by appending IDs; never renumber existing
ones.

## Lean conventions

Detailed mechanics for several of these live in `CONTRIBUTING.md` under **Lean
Style**; the rule here is the normative summary.

- **LEAN-1 — Mathlib alignment.** Follow the
  [Mathlib style guide](https://leanprover-community.github.io/contribute/style.html)
  and [naming conventions](https://leanprover-community.github.io/contribute/naming.html),
  except where an SFL pedagogical convention below overrides them.
- **LEAN-2 — Idiomatic Lean.** Definitions and proofs are written the way a
  working Lean engineer would write them. Depart from idiom only temporarily and
  only for pedagogy, and say why (LEAN deviation marker).
- **LEAN-3 — Tactic discipline.** Introduce and use tactics in the established
  order (`CONTRIBUTING.md`, "Tactics: order of introduction"). Never use a
  tactic in a chapter before the point where it has been taught.
- **LEAN-4 — Naming and namespaces.** Follow the naming/namespace rules in
  `CONTRIBUTING.md` ("Names and namespaces"); names are descriptive and match
  the surrounding development.
- **LEAN-5 — Argument visibility.** Choose implicit vs. explicit arguments per
  `CONTRIBUTING.md` ("Theorem arguments and visibility").
- **LEAN-6 — Clean elaboration.** Finished material elaborates with no linter
  warnings and no stray `sorry`/`admit`. Intentional incomplete code, expected
  errors, and diagnostics use the mechanisms in `CONTRIBUTING.md` ("Incomplete
  code, expected errors, and diagnostics").
- **LEAN-7 — Notation and simplification.** Introduce notation deliberately and
  keep `simp`/normal-form usage consistent with `CONTRIBUTING.md` ("Notation and
  simplification").
- **LEAN-8 — Definitions vs. abbreviations.** Follow `CONTRIBUTING.md`
  ("Definitions vs. Abbreviations") when choosing `def` vs. `abbrev`.
- **LEAN-9 — Custom arithmetic.** Use SFL's custom `Nat`/arithmetic where the
  chapter calls for it (`CONTRIBUTING.md`, "Arithmetic / the custom `Nat`").

## Pedagogical and presentational conventions

- **PED-1 — Exercise-based.** Every important concept is reinforced by hands-on
  exercises, each with a solution.
- **PED-2 — Progressive sophistication.** Concepts, tactics, and proof idioms
  are introduced small and grown deliberately; nothing depends on material a
  reader has not met yet.
- **PED-3 — Proofs teach proof engineering.** Proofs are themselves examples:
  readable, maintainable, and idiomatic, not merely closing the goal.
- **PED-4 — Motivate before formalizing.** Introduce the idea and its purpose in
  prose before the Lean that formalizes it.
- **PED-5 — Consistent chapter structure.** New chapters follow the structure,
  sectioning, and rhythm of existing chapters.
- **PED-6 — Presentational polish.** Displays, notation, tables, and figures are
  held to a high visual bar and kept consistent across chapters; diagrams carry
  an ASCII fallback (`CONTRIBUTING.md`, "Diagrams with ASCII fallback").
- **PED-7 — Connect to CSLib.** Where natural, relate SFL developments to
  [CSLib](https://github.com/leanprover/cslib/tree/main) (Guiding Philosophy,
  tenet 4).

## Writing style

- **WRITE-1 — Chicago Manual of Style.** For any grammar, punctuation, or usage
  question not settled here, follow the
  [Chicago Manual of Style online edition](https://www.chicagomanualofstyle.org/).
- **WRITE-2 — American spelling and the serial comma.** Use American spelling
  and the serial (Oxford) comma, per Chicago.
- **WRITE-3 — Voice.** Address the reader as "you"; the authors are "we." Prefer
  the active voice.
- **WRITE-4 — Tone.** Clear, direct, and encouraging. Introduce technical terms
  and jargon at first use.
- **WRITE-5 — Code in prose.** Set identifiers, tactics, and code fragments in
  `backticks` (or a `lean` block); never as plain prose.
- **WRITE-6 — Headings and titles.** Use the heading style of the surrounding
  chapter; keep capitalization consistent within a document.
- **WRITE-7 — Concision.** Prefer the shorter, plainer wording; cut throat-
  clearing ("it is worth noting that", "basically") and redundancy.

## Checking these conventions

These conventions are meant to be **normative and audited semi-automatically**.
Each is tagged with how it can be checked:

| Class | Meaning | Enforcement |
|---|---|---|
| **auto** | Mechanically decidable (regex / Lean AST / linter) | Runs in CI on every PR |
| **assisted** | A script surfaces *candidates*; a human confirms | Periodic report, human adjudicates |
| **manual** | Judgment-based (pedagogy, prose quality) | Periodic LLM-assisted + human review |

The intended machinery (see `CONTRIBUTING.md` once built):

1. **Single source of truth.** This file, with stable IDs, is what every check
   references. A check's output names the ID it enforces (e.g.
   `LEAN-6: sorry in finished material at LF/Poly.lean:212`).
2. **`make style-check`.** A `scripts/style_check.py` runs the *auto* checks and
   the *assisted* candidate-finders, printing violations grouped by ID. CI runs
   the auto subset on every PR; the assisted subset is advisory.
3. **Periodic style audit.** For *manual* conventions, an LLM-assisted pass runs
   over the material changed since the last audit (or a sampled chapter),
   using a checklist derived mechanically from this file, and produces a report
   keyed by ID for a human to adjudicate. Cadence: per release, or monthly.
4. **Marked deviations.** A permitted pedagogical deviation is annotated inline
   next to the code/prose it applies to, naming the ID and reason, e.g.
   `-- style: LEAN-2 (kept non-idiomatic for teaching)` in Lean, or a `:::dev`
   note in versified prose. Checkers skip a flagged item whose marker names the
   ID they enforce, so audits stay quiet on accepted exceptions.
